## Language Applicability Notes

**Explanations (Problem Statement, Approach, Examples) are always language-agnostic** — written in plain English describing the concept and logic, never tied to any one language's syntax. Only the **Code Solution** section varies per language (`+ Add Language` in the CMS).

This means the applicability question only affects which languages get a Code Solution for a given problem:

- **Universal concepts** (Foundations, OOP, Error Handling, Design Patterns, Clean Code): the concept and logic are identical across languages — strong candidates for Python + Java + JavaScript code solutions, since a student can compare idiomatic syntax side by side for the exact same explanation.
- **Mostly universal, syntax varies more** (Collections): same underlying idea across languages (list-like, map-like, set-like structures), so still worth multi-language code, just expect more naming/behavior differences between the solutions themselves.
- **Language-specific idioms** (Generators, Decorators, Async/Await): the explanation still stays language-agnostic (e.g., "a generator produces values lazily, one at a time, instead of computing them all upfront"), but not every language has a directly equivalent construct — so these get a primary code solution in the language where the idiom is most natural (Python), with a second-language version added only where a genuinely comparable construct exists (e.g., JS generators), rather than forcing a language that doesn't have the feature.
- **Recommended default set of languages per Code Solution:** Python + Java + JavaScript for most problems; add C++ selectively for Memory Management and Concurrency, where a lower-level language adds real teaching value.
